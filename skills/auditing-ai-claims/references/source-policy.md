# Source and evidence policy

## 层级不等于独立性

| 层级 | 典型来源 | 可直接支持的最窄陈述 |
|---|---|---|
| A1 | 法规、监管文件、论文全文、财报、官方数据、代码、可复现实测 | 原始记录在限定条件下写了什么 |
| A2 | 公司产品页、新闻稿、模型卡、管理层陈述 | 该主体作出了什么自述 |
| B | 有方法和出处的专业二手分析 | 对原始材料的专业解释或复核 |
| C | 普通媒体、社交媒体、未给原文的转述 | 搜索线索 |

另一个 AI 回答不是证据。

## 证据角色

每条来源必须标记：`original_record`、`subject_self_report`、`independent_replication`、`regulatory_record`、`professional_analysis`、`secondary_report` 或 `lead_only`。

公司能权威说明自己的当前价格、条款和公开声明，但公司自测不能单独证明客观性能、行业排名或独立有效性。

`objective_performance` 是独立主张类型，适用于模型跑分、产品效果、准确率、速度、排名和其他被描述为客观性能的结论。A2 或 `subject_self_report` 可以证明主体作出了性能声明，不能单独把该性能本身标成 `confirmed`。要确认客观性能，必须找到与对象、版本、任务、指标、样本、比较集和测试条件相匹配的独立材料或可复现实测。

## 根来源

`origin_id` 标记证据真正来自哪里。三篇媒体都转述同一新闻稿时，三者使用同一个根 ID。链接数量不能洗成证据独立性。

只有以下严格持久标识格式可以进入独立性计数：

- `doi:10.<注册机构>/<后缀>`
- `pmid:<数字>`
- `nct:NCT<数字>`
- `filing:<法域或登记系统>:<文件号>`
- `regulation:<法域或登记系统>:<文件号>`
- `court:<法域或法院>:<案号>`
- `dataset:<发布机构>:<数据集标识>`
- `commit:<7 至 64 位十六进制提交哈希>`

其他自由文本、URL、媒体名、`unknown:`、`claimed:` 或自造标签可以留作追踪，但不能建立独立证据根。格式通过也只是机器门的必要条件，不自动证明标识真实；仍需 `source_identity` 精确证据核对标识、作者、版本和正文对象。需要独立证据的确认状态至少要有两个不同的合格持久标识、两个不同最终 URL 和两个不同内容哈希。只要用于独立性候选的直接实体证据里混入未识别根，独立性门就失败。

## 当前性

价格、现任职位、法律状态、当前产品能力和“最新”属于高时效主张。必须同时记录：

1. 主张 `as_of`
2. 来源发布日期，未知时明确写 `unknown`
3. 访问时间，由回执生成
4. `freshness_status` 为 `current`、`stale` 或 `unknown`
5. 非空的 `freshness_rationale`，说明为何该访问时间和页面状态足以代表核验日

运行时不会假装存在通用有效期。审计者应根据价格变更频率、法律生效日、产品版本和页面性质判断当前性，并说明理由。

## 支持范围

比较来源和主张时至少检查：对象、版本、时间、人群、任务、法域、指标、比较集和条件。

一个 benchmark 只能支持该版本、题集、指标和设置。调查中的群体相关性不能自动变成对所有人的长期因果结论。NIST 等通用框架不能自动变成某产品的认证。

所有 `direct`、`partial` 和 `conflict` 证据都必须写非空 `support_scope`，明确来源实际覆盖的最窄范围。只有标题、摘要式转述或“这条支持主张”不构成范围记录。

## 证据用途

每个证据连接必须说明它在判断中承担什么工作：

| `evidence_purpose` | 要回答的问题 |
|---|---|
| `substantive` | 正文是否直接支持、部分支持或冲突于主张内容 |
| `study_design` | 原文是否明确写出能承载因果推断的研究设计 |
| `source_identity` | 来源、作者、论文标识、文件版本是否就是所声称的对象 |
| `currentness` | 来源日期、访问状态和版本是否足以代表核验日 |

同一来源可以承担多个用途，但每次连接只记录一个用途和对应精确范围。用途标签不是证据强度，也不能自动兼任其他用途。比如公司页面的 `source_identity` 引文可以证明页面属于该公司，不能因此成为独立性能证据。

决定性状态执行四条用途隔离：

1. `confirmed`、`partially_supported` 和 `refuted` 都需要 `source_identity` 的直接、可复现引文。
2. 内容支持门只使用 `substantive`。`confirmed` 要直接实体支持，`partially_supported` 要直接或部分实体支持，`refuted` 要直接实体冲突。
3. 高时效主张的决定性状态必须另有 `currentness` 的直接、可复现引文或已定位的当日记录。
4. 因果主张进入 `confirmed`、`partially_supported` 或 `refuted`，必须同时记录合格 `causal_basis`，并连接用途为 `study_design` 的直接、可复现引文。只由审计者填写一个设计名称不够。

## 来源生命周期

来源一经登记就进入账本并默认 `active: true`。可用来源、失败抓取和上下文导入都保留回执，不能通过改写账本假装它们从未发生。

当活动来源尚未连接主张且确定不再纳入本次判断时，可以退役该来源；常见场景是失败抓取阻挡 gate。退役记录包括 `active: false`、`retired_at` 和 `retirement_reason`。退役不会删除原始回执或工件，也不把失败材料变成合格证据。已经连接主张的来源不能用退役绕过冲突或缺陷。

来源若出现在 countercheck 的 `checked_source_ids`，必须在记录时仍为活动来源。之后退役会使该 countercheck 失效，必须重新检查并记录新的停止理由。决定性状态的反证环节不能用空来源列表，也不能用失败或 `support_eligible: false` 的来源得出确定反向结果。

来源登记使用不可变工件和事务日志。事务没有进入 `committed` 或明确的 `aborted` 终态前不能通过 gate；同一 source ID 只允许用完全相同的冻结元数据恢复。若崩溃发生在工件完整落盘前且原响应无法复现，可以保存非空理由将事务终止为 `aborted`。该状态保留快照和已有字节，不产生账本来源，source ID 永久不能复用。不得删除或手写事务日志来隐藏失败阶段。

## 获取方式

- `runtime_fetch`：运行时自己完成受控网络抓取
- `browser_export`：调用方声称由外部浏览器导出的内容，只作上下文或待核材料
- `trusted_local_copy`：调用方声称来源明确的本地文件，只作上下文或待核材料
- `user_supplied`：用户提供但未独立认证，只作上下文或待核材料
- `search_snippet`：只能定位，永远不能支持确认或反驳

当前运行时只有通过工作区 HMAC attestation 的 `runtime_fetch` 可以进入确认或反驳的硬门。格式正确但未认证的手写回执不具备支持资格。HMAC 只证明回执走过持有本地密钥的运行时路径，不证明远端来源真实，也不抵御密钥被取得或本机已被控制。`capture` 会保存文件、哈希和调用方声明，但不能自行证明文件与所填 URL 的绑定关系，因此返回非零并写入 `support_eligible: false`。未来若接入独立连接器证明，必须另行定义不可由调用者自填的传输回执和派生文件谱系。

PDF 的 `runtime_fetch` 只有在本机 `pdftotext` 成功解析、输出为非空 UTF-8、解析器版本可识别且文本工件哈希可复验时，才可能进入证据硬门。解析器缺失、超时、失败、输出过大或空文本都会保存 `parser_error` 并保持 `support_eligible: false`。运行时不自动下载解析器，也不做 OCR。

回执中的 URL 不保存查询参数明文，只保存无查询串的 URL 与查询串哈希。审计工作区默认仅所有者可读，并带局部 `.gitignore`；这降低误提交风险，但不替代用户对输入和来源材料的隐私判断。

页面打不开、登录受限、404 或正文缺失时，记录失败并停在无法核验。404 只说明当日该地址没有成功返回目标内容，不证明某对象永久不存在。
